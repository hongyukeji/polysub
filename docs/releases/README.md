# 发布说明维护

README 面向安装和使用，CHANGELOG 汇总版本历史，GitHub Release 描述这一版的变化。三者不要互相整篇复制。

## 文件与流程

- 每个版本一个文件，例如 `0.3.2.md` 对应标签 `v0.3.2`。从 [TEMPLATE.md](TEMPLATE.md) 复制，填写实际变化，删除没有内容的分类；不要发布占位符或未经验证的结论。
- 发布标题统一为 `PolySub 版本号`，正文不重复一级标题。
- 推送标签后，发布工作流先检查版本号和对应说明文件，再测试、打包、签名，最后用该文件创建**草稿**。
- 下载草稿附件完成验证后，把真实结果写进说明文件并提交，用 `gh release edit v版本号 --notes-file docs/releases/版本号.md --draft=false` 更新正文并公开发布。不要提前把预计完成的测试写成「已通过」。
- 公开发布后，[hongyukeji/homebrew-tap](https://github.com/hongyukeji/homebrew-tap) 在 30 分钟内自动更新配方（也可在该仓库手动运行 Sync releases）。

编辑已发布版本的说明时，只调整文字、链接和结构，保留该版本的真实行为、资产和标签。校验和与验证结果必须对应原发行产物。

## 内容与排版

1. **一句话摘要**：这一版解决的主要问题。
2. **更新内容**：按实际内容使用「新增」「修复」「改进」分类，用简短条目写用户能感知的变化；有相关提交时附链接。
3. **下载与安装**：表格列出发行包和校验文件，链接到 README 的三种安装方式。历史版本要说明 Homebrew 安装的是当前最新版。
4. **升级说明**：写清用户是否需要额外操作。
5. **验证与限制**：列出实际完成的检查，区分自动化与本机验证；未公证、未覆盖的环境要写明。
6. **完整变更**：用相邻标签的 compare 链接；没有上一个公开版本时链接本版本源代码。

正文里的文件链接用完整 GitHub URL。会随时间变化的操作文档链接 `main`；历史证据链接到具体的 CI 运行或提交。
